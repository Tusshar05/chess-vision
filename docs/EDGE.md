# Edge and mobile deployment

What is **implemented and measured** here: CPU inference with ONNX Runtime (FP32 and static INT8)
and CoreML export; numbers in [`reports/benchmark.md`](../reports/benchmark.md) (generated by
`make bench` on the author's Mac). What is **untested** is marked as such.

## Why the models are edge-friendly
- YOLO11n: ~2.6 M parameters, ~6.5 GFLOPs at 640 px; two such models (pieces + corners).
- Both models run in a single forward pass each - no per-square classifier, no sliding window.
- The pipeline needs no PyTorch at serving time; geometry is a 3x3 homography (OpenCV).
- Pre-processing is one area downscale + letterbox; post-processing is NMS + a 3x3 matrix multiply.

## Implemented: exports
| Target | How | Notes |
|---|---|---|
| ONNX FP32 | `make export` (`ml/export.py`) | fixed input size, simplified, opset 17 |
| ONNX INT8 | same | static QDQ, per-channel, calibrated on 50 train/val images |
| CoreML | same (`coremltools`) | `.mlpackage`, FP16, run via `ultralytics` on macOS |

INT8 caveat: on this Apple-silicon CPU ONNX Runtime's QDQ INT8 is not guaranteed to beat FP32
(quant/dequant nodes cost time on small convnets); the benchmark reports both latency and the
accuracy change so the trade-off is measured rather than assumed.

## iPhone (on-device) - path, not shipped
1. Use `weights/detector.mlpackage` and `weights/corners.mlpackage` from `make export`.
2. Add them to an Xcode project; Xcode generates Swift classes. Use the Vision framework
   (`VNCoreMLRequest`) or call `MLModel` directly with a 640x640 (letterboxed) image.
3. The models were exported with `nms=False`: the raw head tensor is returned. Port
   `decode_detections` / `decode_corners` (`ml/chessvision/onnx_infer.py`, ~40 lines of NumPy) and
   `homography` + `cell_to_square` (`ml/chessvision/board.py`) to Swift - `getPerspectiveTransform`
   is available through OpenCV for iOS or can be solved directly (8x8 linear system).
   Alternatively export with `nms=True` for the detector and let CoreML do the NMS.
4. Run the Neural Engine path by keeping FP16 and fixed shapes; measure with Instruments.
5. Stockfish on-device: use a Stockfish iOS build (GPL-3.0 implications for distribution) or call
   the REST API for analysis only.

## NVIDIA Jetson (TensorRT) - **UNTESTED**
No Jetson hardware was available; this is the expected path, not a result.
1. Copy `detector.onnx` / `corners.onnx` to the Jetson (JetPack 6, TensorRT 10).
2. Build engines: `trtexec --onnx=detector.onnx --saveEngine=detector_fp16.engine --fp16`
   (INT8 needs a calibration cache; reuse the same 50 calibration images).
3. Replace the ONNX Runtime session in `OnnxDetector` / `OnnxCornerModel` with the ORT
   TensorRT execution provider (`providers=["TensorrtExecutionProvider", "CUDAExecutionProvider"]`)
   or the TensorRT Python API - the decode/NMS/geometry code is unchanged.
4. Expect the whole pipeline to be limited by camera capture and JPEG decode, not the models.
5. Benchmark with the same `ml/benchmark.py` harness (add a backend) and publish numbers only after
   running it.

## Other options considered
- **ONNX Runtime Mobile / ORT-Android:** same ONNX files, `.ort` format conversion; good Android path.
- **TFLite:** would need a converter chain (ONNX->TF->TFLite) with op-support risk; not pursued.
- **WebAssembly (onnxruntime-web):** feasible for an in-browser demo (INT8 helps download size).
